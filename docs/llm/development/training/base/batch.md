title: Batch
---

Batch 是一次参数更新所聚合的样本集合；全局 batch 由每卡 batch、设备数和梯度累积步数共同决定。它的意义在于：batch 越大，单次更新的梯度估计越稳定、硬件利用率越高，但也越占显存，因此需要显式拆分与累积来在二者间权衡。

## 快速开始

先算清全局 batch，再决定如何实现它。核心公式是：

$$\text{global\_batch} = \text{micro\_batch} \times N_{\text{DP}} \times G_{\text{acc}}$$

其中 micro batch 是每个数据并行卡上一次前向/反向处理的样本数，$N_{\text{DP}}$ 是数据并行 GPU 数，$G_{\text{acc}}$ 是梯度累积步数。将全局 batch 与学习率、训练步数一同记录，这三者共同决定训练预算和收敛行为。

先用不 OOM 的 micro batch 运行，确认单步能通过，再通过梯度累积或更多 GPU 扩大有效 batch。梯度累积不增加显存但也不减少计算量，只是把多次 micro step 的梯度累加后统一更新。当损失按样本数求均值时，梯度累积等价于把 $G_{\text{acc}}$ 个 micro-batch 的梯度求平均，即得到全局 batch 的梯度：

$$g_{\text{global}} = \frac{1}{G_{\text{acc}}}\sum_{k=1}^{G_{\text{acc}}} g_k$$

其中 $g_k$ 是第 $k$ 个 micro-batch 的梯度。这是「micro batch 小、但全局 batch 不变」能保持优化语义一致的原因，前提是损失做的是均值归约而非求和。

日志和学习率调度应按优化器更新步对齐，而不是按 micro step 前进，否则梯度累积时调度器会错误地提前衰减学习率。例如 $G_{\text{acc}}=4$ 时，每 4 个 micro step 才对应一次优化器更新，学习率调度与 checkpoint 都应以此步为基准。

## 影响

较大的 batch 通常降低梯度噪声、提升硬件利用率，因为单步样本更多，梯度估计更稳定，矩阵运算的并行度也更高。但它会占用更多激活显存，因为更多样本的前向激活需要同时驻留在显存中，micro batch 太大就会 OOM。

增大 batch 通常还需要同步调整学习率和训练步数：batch 增大后若学习率不变，更新步数减少可能影响收敛。早期工作（如 [Accurate, Large Minibatch SGD](https://arxiv.org/abs/1706.02677)）提出 batch 扩大 $k$ 倍时学习率同步扩大 $k$ 倍的线性缩放经验，但它有适用边界，batch 过大时梯度噪声过低反而可能损害泛化。常见做法是配合学习率缩放或重新评估总训练步数，这些调整应基于短时实验验证，而非盲目套用固定比例。

对变长文本，应同时记录 token batch 而不只记录样本数：同样 8 条样本，token 总数可能相差数倍，计算量和梯度统计完全不同。固定序列长度或按 token 计量才能公平比较不同配置的吞吐与训练预算，换算关系为：

$$\text{token\_batch} = \sum_{i=1}^{B} l_i \approx B \times \bar{l}$$

其中 $B$ 是样本 batch，$l_i$ 是第 $i$ 条样本的 token 长度，$\bar{l}$ 是平均长度。

## 案例：按 token 计量

两组实验都使用 8 条样本，但一组平均 512 token、另一组平均 4,096 token。两者样本数相同，但后者的浮点运算量约为前者的 8 倍，梯度统计的有效样本量也完全不同，直接用「每步 8 条样本」比较吞吐或收敛会严重失真。

正确的做法是记录每步有效 token 数（8 条 × 平均长度），用它来比较吞吐 (token/s) 和训练预算。当使用序列打包把变长样本拼成接近固定长度的序列时，token batch 是更准确的衡量口径。

不同配置只有在对齐 token 预算后才有可比性：例如把样本数减半但长度加倍，token batch 不变，此时计算量相近，但仍需确认序列长度分布变化对梯度统计的影响。
